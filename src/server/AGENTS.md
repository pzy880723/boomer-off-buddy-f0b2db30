# Support conversation rules
- Support conversations: external replies only by primary_agent_id with matching assignment_version, enforced inside DB RPCs (support_update_assignment / support_staff_post_message) in one transaction; internal notes open to any authorized collaborator. Why: prevents race between old owner and HQ takeover.
- Support context location is derived server-side (order lines → single store else HQ null; product → listing location); open conversations dedupe on customer_id + context_key. Why: client-provided store is untrusted.
- Support message presentation is resolved after conversation authorization using each sender's conversation participant role, customer-owned avatar, linked shop image, and server-controlled HQ metadata; GET and POST share an explicit safe projection. Why: prevents historical-owner substitution and disclosure of private URLs or staff identifiers to customers.
- Handheld AI consent: every real AI/research request takes a required AiOutboundGuard (src/server/ai-guard.ts) checked immediately before the fetch; handheld guards bind the session or queued job's original actor + policy version and re-read public.handheld_ai_consents each time, PC ERP callers pass webErpAiGuard() explicitly and handheld-only modules reject it; detail-image jobs get actor/policy inside the handheld_product_content transaction (6-arg overload). Why: revocation must stop the next outbound stage, there is no default-allow path, and jobs can never be attributed after the fact.

- Storefront discovery (storefront_product_opens/favorites/search_term_hits, migration 0048) is service-role only; customer identity comes only from the verified consumer token, search records only vocabulary-matched terms with per-day hashed visitor keys, and popular = 30-day distinct openers + 3×current favorites sorted before paging. Why: no forged totals, no personal search history, stable paging.

- Paid-order handheld alerts (migration 0049): DB triggers write one inv_handheld_notifications kind=order_paid row per fulfillment (unique ref_id) when a storefront order becomes paid or a fulfillment appears on a paid order; refund/cancel sets action_status=voided, picking sets handled; failures only WARN. Payload carries ids/order_no/fulfillment_method/sales_origin only, never phone or address. Why: callback replays cannot duplicate, each store gets its own alert, and alerting can never roll back a payment.

- Manual shipment entry (ERP web and handheld /fulfillments/:id/manual-ship) goes only through commerce_manual_ship_fulfillment (0050, hardened by 0053): validate everything before any write, whole-fulfillment lines equal to shippable qty (expected minus approved shortages), content-fingerprint idempotency, picked_qty only topped up; non-SF/Cainiao couriers use provider=manual with carrier_label; one transaction with row locks, actor store scope checked in DB, paid non-pickup non-after-sale orders only, client_op_id idempotent with conflict detection. Handheld pickup ready/redeem routes call the existing pickup RPCs with session actor and device location. Why: one safe business path, no UI-side authorization, no partial writes.
- Shortage/refund clearance for fulfillment (manual ship, complete pick, pickup ready/redeem, handheld pick guard) is decided only by DB helpers from 0054 (commerce_shortage_refund_cleared / commerce_order_settlement_block / commerce_fulfillment_pick_facts): cleared = accepted shortage → succeeded intent → succeeded commerce_refunds with matching after-sale, payment and amount; partially_refunded passes only when every successful refund maps to a cleared shortage. Lock order is order → fulfillment → items. Why: refund_state strings and payment_status alone drift from the real worker chain (succeeded / partially_refunded).
- Handheld notification visibility (REST filter and handheld_notifications_changes) = location is null or in the effective stores (explicit authorized location_id, else all authorized) AND (targeted to the user, or untargeted-user with no device or this device). Why: same-store notices addressed to another staff member or device must not leak, and a store switch must not show other stores.

- Youzan is the sole authority for member points. Customer/POS points come only from youzan-points-projection*.server.ts (read-only points.get + official changelog mirror via service_role RPCs, version-monotonic, failures keep last Youzan data, never fall back to local wallet or 0). The ERP self-run ledger (points-earning.server.ts, commerce_points_record_order_*) stays dormant behind both off switches and must not feed customer-facing balances. Why: checkout runs natively in Youzan; two ledgers would diverge.
- Measurements: store = inv_stocks qty>0 only (no inv_skus.location_id); RPCs lock SKU, plain-read stock; request + deferred stock trigger share ONE global routing lock (trade-off: few stores, routing serialized for correctness; trigger never locks SKU/stock); claim via measurement_claim; writes try actor+op+exact-body (incl. location) replay first; ready diagram only via upload + asset_register. Why: no lock cycles/missed moves, lost responses confirmable.
- Legacy product-content backfill: scripts/backfill-product-content.ts (dry-run default, ≤20/batch) builds via buildAutoProductContent with sku-listing/ images only; eligibility, version CAS, idempotency and backup/restore live only in product_content_backfill_* DB functions; sources persist in inv_product_content.auto_sources and are returned by published_product_content; system-written content (readiness template, backfill) sets updated_by = content_system_actor(), never an employee; listing_readiness tests must pass schema_check.sh against real_schema_*.txt. Why: one fail-closed path, no manual-edit overwrite, reversible; real NOT NULLs are not hidden by loose stubs.
- Flash COD (同城闪送到付): fulfillment_method='flash', courier SHANSONG_COD/provider 'flash', platform shipping fee always 0 and delivery_fee_payment='cod' (fee is negotiated via store support and collected on delivery, never online); quote/create authority is commerce_quote_checkout_v2('flash') + commerce_create_ordinary_flash_order (per-store location ownership enforced in DB per listing, snapshot compared, idempotent replay, method conflict rejected); delivery is registered only via commerce_flash_deliver_fulfillment (no tracking number; same permission/settlement/shortage/lines/idempotency checks as manual ship), and commerce_manual_ship_fulfillment rejects flash orders ('flash_order') so no fake courier numbers. Why: one atomic DB path, no fee collection, no cross-store or HQ misrouting.

- Measurement conversations reuse product context only at the task’s current store; a different-store active context uses a task/store-specific key without moving prior questions, under task locks and exact requester validation. Why: transfers cannot leak customer questions to another store.
