# Commerce product rules
- Bargain-basket (翻筐乐) eligibility is computed only by src/lib/commerce/fankuang.ts from inv_skus.fankuang_override (NULL=auto by price threshold, explicit boolean wins); only tracked custom single SKUs qualify; storefront filters before paging. Why: one rule for ERP, handheld and storefront.
- Product featured stamp / notice tags live only on inv_skus.featured_stamp + notice_tags; the key dictionary and Chinese labels come only from src/lib/commerce/product-marks.ts, mirrored by DB CHECK + handheld_item_update validation (uncertain/unavailable exclusive); storefront/handheld DTOs expose keys via readProductMarks. Why: one whitelist enforced server-side, UI never shows raw keys.
- Category display names come only from src/lib/commerce/category-labels.ts (inv_categories dictionary, seed Chinese fallback); unknown codes yield name=null/path=[] — never the raw code or a placeholder. Handheld DTOs add category_name/category_path/mark_labels alongside the unchanged category code. Why: no English codes leak to customers or staff.
- ERP batch mark edits go only through batchUpdateProductMarks → src/server/product-marks-batch.server.ts: session roles (HQ or store_manager limited to SKUs stocked at their stores), plan via planMarkChange, per-item updated_at CAS writing only the target field, per-item success/unchanged/skipped/failed; batch never adds "flawed". Why: no silent overwrite, no fake success, defect annotation stays per item.
