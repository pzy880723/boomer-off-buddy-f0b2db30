# Architecture rules
- Support, points-earning and measurement rules live in src/server/AGENTS.md; membership/newcomer coupon rules in src/lib/membership/AGENTS.md; commerce product rules (翻筐乐, stamps/tags) in src/lib/commerce/AGENTS.md.
- PC card printing adapts the native same-origin array manifest and embeds original single-card PDF pages without rasterization; eligibility is rechecked before output. Why: preserves embedded fonts and approved layouts while blocking retired presets.
- Card spec filtering uses exact manifest dimensions; homogeneous hook-card selections use a dedicated packing branch, mixed selections keep the general packer. Why: avoids orientation-based misclassification.
- PC QR reads use authenticated server functions with handheld role/location and private-object path semantics, never device credentials. Why: web users have no device token and QR assets stay store-isolated.
- Youzan push callbacks: with Event-Sign header verify MD5(client_id + raw body + client_secret) only, no body.sign fallback; header-less legacy messages are read-only hints and stay blocked. Why: only the raw body is covered by the official signature.
- Youzan member-asset notifications only trigger read-only re-queries into youzan_member_asset_observations; never write wallets, coupons or the points ledger. Why: outer fields are unsigned and the ERP is the single ledger.
- Custom print cards: service_role only after handheld device+session and location authorization; AI copy jobs use the listing-image-worker hook with DB lease/job_token claim; only super_admin converts custom→preset via one version-CAS update. Why: store isolation server-side, survives app exit, atomic idempotent publish.
- Youzan sale stock deduction keys units by trade tid + line oid; commit_youzan_sale_line checks exact and reordered legacy positional events under the order lock (ambiguity rejects), counts only processed events, retries failed ones boundedly via commit_sale; order-sync queue stays order-only; recovery is only the flag-gated ≤72h keyset-paginated compensation for tracked custom single SKUs with location/stock/restock/refund guards; trade-push business failures return non-success for platform retry. Why: no double deduction across key formats or reordering, no starvation, standard items and historical imports untouched.
- channel-sync-worker accepts only the service-role Bearer, claims via claim_channel_sync_tasks_v2 (expired-lease reclaim, canary filters), finishes only via finish_channel_sync_task with worker fencing; set_stock_zero/delist re-read SKU version, sales_state, is_display, real inv_stocks and listing ownership before any Youzan write (read failure blocks; active/in-stock/newer tasks superseded); dead_letter never closes the sale loop; Tencent systemd timer is the only scheduler. Why: stale sale tasks must not zero/delist restocked items; a lost lease must not report success.
- Sale-sync release acceptance checks every active branch's location/warehouse mapping, scan progress, unfinished tasks, real stock and branch visibility; verify timer API results via the current symlink, not exit status. A branch with no real custom sale is config/read-path verified only. Why: a healthy process is not evidence every store's data path works.
- Store pickup credentials (commerce_pickup_codes) are issued by DB triggers inside the verified-payment transaction, one per store sub-order, redeemed only via SECURITY DEFINER RPCs re-checking staff store scope, payment/refund/shortage state and readiness under row locks; customer detail exposes credentials only after ownership checks. Why: codes cannot change on payment replay, be redeemed cross-store or after refunds, or be bypassed by UI.
- Staff name/avatar are maintained only by super_admin in PC ERP; canonical source is Auth user_metadata.name + avatar_path in the private staff-avatars bucket (service-role only), signed at read time; handheld/GO/web profile endpoints read live metadata server-side, read-only. Why: shared accounts see one identity; stale JWTs and expired URLs never become truth.
- Review demo isolation: src/server/review-isolation.mjs (BOOMER_REVIEW_ISOLATED=true) refuses production data/real channels at boot and blocks external writes. Why: review never touches real systems.
- Listing readiness: readiness row in SKU insert tx; smart-create v2 (also standard-reuse append; route skips image_paths) persists plan+uploader and queues AI jobs in the commit tx; raw photos settle only via queued jobs or explicit decline; worker sweep resolves pending consent; published listings park new images in pending_display until ready; edits bump revision, release SKIP LOCKED. Why: fail-closed, crash-safe, no half-processed public display.
- Display names for fields/attributes come only from src/lib/attribute-labels.ts; unknown keys hidden. Why: one Chinese dictionary.
- Web batch context is keyed by account, roles, authorized locations, selected location and filters; context changes unmount the sheet, confirmed requests are copied and failed-only retries retain their original versions. Why: late receipts and refreshed versions must never affect another operation or overwrite an intervening edit.
- Batch version comparison normalizes timezone offsets separately from fractional digits up to nanoseconds; CAS receives the original confirmed token, and all roles including HQ intersect selections with explicit current-location stock records. Why: same-millisecond edits and HQ scope bypasses must never overwrite or reach another store.
- Batch fankuang planning uses explicit current-location stock and native listing-status/eligibility helpers, leaves non-participant removal unchanged, and rejects unknown old notice arrays before normalization; active/non-standard editing capability and verified role/location checks are retained. Why: legacy cache, hidden products and unknown tags must not yield false eligibility or destructive writes.
- Web product-card entry reuses buildRecommendationCard and its existing copy generator through an authenticated location-scoped wrapper solely for ephemeral copy preview; the dialog explicitly disclaims card creation/storage and clears preview on close, without saving/exporting/printing or changing the native route. Why: a copy response must never be represented as a persisted native card or completed A4 printing workflow.

- Measurement support cards revalidate task-store and exact requester linkage after conversation authorization; pending work uses one SQL aggregation for handheld and ERP, separate from unread events. Why: old conversations cannot disclose moved-store cards, and multi-entry counts stay consistent.
- Member onboarding uses service-only per-shop revision/token leases; nonblocked SQL receipts require complete HQ fingerprint/scope/identity and explicit native inheritance. Only classified transient worker/projection failures retry after 15 minutes below three attempts, without reset or notifications. Tencent organization reads exhaust explicit bounded pagination, and customers/projections use upper-bounded keysets; branches reference HQ only. POS/local-wallet and unverified inheritance stay blocked; no writer. Why: omitted evidence, shrinking offset pages and unlimited retries cannot prove safe complete acceptance.
- POS policy loading uses trusted HQ identity plus read-only projection and current onboarding fingerprints, exposes display evidence separately from disabled redemption, and quote/sale handlers reject nonzero points after authorization before transactions; no rule/wallet fallback or database transaction changes. Why: a configuration mirror and display balance are not a spending authorization or an idempotent provider debit/refund contract.
- Meluo standard onboarding is a separate exact-target immutable 14×32 plan; the broad catalog hook is never reused, and channel append execution remains blocked until its official partial-update semantics are verified. Why: targeting one store alone does not prevent shared-master or inventory mutations.
