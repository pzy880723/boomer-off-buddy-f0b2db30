# Architecture rules
- PC card printing adapts the native same-origin array manifest and embeds original single-card PDF pages without rasterization; eligibility is rechecked before output. Why: preserves embedded fonts and approved layouts while blocking retired presets without new permissions.
- Card specification filtering uses exact manifest dimensions; homogeneous hook-card selections use a dedicated physical packing branch, while mixed selections retain the general packer. Why: avoids orientation-based misclassification and preserves existing mixed-layout behavior.
- PC QR reads use authenticated server functions with the handheld role/location and private-object path semantics, without borrowing device credentials. Why: web users have no device token and original QR assets must remain store-isolated.
- Youzan push callbacks: when the Event-Sign header is present, verify MD5(client_id + raw HTTP body + client_secret) only, with no fallback to body.sign. Header-less legacy body.sign messages are read-only hints and stay blocked. Why: only the raw body is covered by the current official signature.
- Youzan member-asset notifications only trigger read-only re-queries into youzan_member_asset_observations. They never write wallets, coupons or the points ledger. Why: the outer fields are unsigned and the ERP is the single ledger.
- Support conversations: external replies only by primary_agent_id with matching assignment_version, enforced inside DB RPCs (support_update_assignment / support_staff_post_message) in one transaction; internal notes open to any authorized collaborator. Why: prevents race between old owner and HQ takeover.
- Support context location is derived server-side (order lines → single store else HQ null; product → listing location); open conversations dedupe on customer_id + context_key. Why: client-provided store is untrusted.
- Support message presentation is resolved after conversation authorization using each sender's conversation participant role, customer-owned avatar, linked shop image, and server-controlled HQ metadata; GET and POST share an explicit safe projection. Why: prevents historical-owner substitution and disclosure of private URLs or staff identifiers to customers.
- Custom print cards (custom_print_cards) are reached only via service_role after handheld device+session and location authorization; AI copy jobs run on the existing listing-image-worker hook with a DB lease/job_token claim, and only super_admin converts custom→preset via a single version-CAS update. Why: keeps store isolation server-side, survives app exit, and makes publish atomic and idempotent.
- Youzan sale stock deduction keys each unit by trade tid + line oid (legacy positional key checked in the same locked RPC commit_youzan_sale_line); the order-sync queue stays order-only, and missed real sales are recovered only by the bounded recent compensation job (≤72h window, fixed floor, refunded/closed skipped, flag-gated). Why: prevents double deduction across key formats and keeps historical imports from deducting stock.
- Store pickup credentials (commerce_pickup_codes) are issued by DB triggers inside the verified-payment transaction, one per store sub-order, and redeemed only through SECURITY DEFINER RPCs that re-check staff store scope, payment/refund/shortage state and readiness under row locks; customer detail exposes credentials only after ownership checks. Why: codes cannot change on payment replay, cannot be redeemed cross-store or after refunds, and UI buttons cannot bypass authorization.
