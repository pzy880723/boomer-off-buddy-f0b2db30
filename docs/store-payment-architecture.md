# BOOMER OFF 自有门店支付架构

## 首期边界

本期只处理总部与自有门店，不包含跳蚤市场寄售商家、市集摊主或其它外部商户进件。

1. 每个 ERP 门店只有一个 `store_payment_profiles`，并拥有唯一、稳定的 `payment_code`。
2. 每个门店支付配置绑定一个营业主体 `payment_subjects`。主体资料、ERP 内审状态、微信申请状态都由 ERP 管理。
3. `payment_code` 是 ERP 内部门店支付身份，不是固定金额的微信收款码。实际收款必须按订单生成动态二维码，以便退款与对账能精确对应订单。
4. 微信 APIv3 密钥、商户私钥和平台证书不得写入前端或数据库，只能进入服务器 Secret Manager。
5. 未完成 ERP 主体认证、微信审核或商户绑定时，收银端必须显示“未开通”，不能伪造支付成功。

## 支付时序

1. ERP 根据订单行的 `location_id` 找到门店支付配置和营业主体。
2. ERP 在 `commerce_order_items.settlement_snapshot` 固化门店、主体、子商户号和行金额。
3. 跨门店订单按支付主体拆成 `commerce_payment_suborders`，订单级运费或优惠按商品金额比例分摊，分摊后总额必须与应付金额完全一致。
4. ERP 服务端调用支付网关，APP、Web 收银台和手机端只拿订单专属支付参数或二维码。
5. 支付回调只进入 ERP；ERP 验签后更新母支付、门店子单和业务订单。

## 申请与认证责任

ERP 是内部申请与配置中心，负责收集资料、校验完整性、提交申请、记录微信审核结果以及绑定门店。最终商户准入仍由微信支付审核，ERP 不冒充支付机构作出外部审核结论。

后续申请完成后，需要在服务器配置：

- 支付网关地址与内部鉴权 Token
- 微信支付 APIv3 密钥
- 商户私钥与证书序列号
- 微信支付平台证书
- 支付回调公网域名

这些值不得提交到 Git，也不得保存为普通数据库字段。
