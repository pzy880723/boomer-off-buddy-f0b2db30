# BOOMER OFF 统一客服落地方案

版本：2026-10-05，方案稿。本文不是已上线证明。

## 1. 最终决策与范围

目标：消费者可以从小程序、APP、微信进入咨询，门店和总部只在 ERP 一个工作台接待；门店先处理，总部可接手，商品、订单、售后上下文不丢失。

架构：微信客服是外部消息渠道，ERP 是客服业务与权限中心。小程序使用微信客服入口；消费者 APP 使用原生聊天页面，复用 ERP 客服接口。不另建互不相通的门店聊天数据库。

2026-10-05 实施优先级纠正：门店主接待终端是 ERP 原生手机 APP 的“消息 → 客户”，不是 PC。网页版是总部配套工作台；两端共用相同会话、权限和接待版本。保留 APP 原有底部栏。M1 先完成文字接待、领取/总部接管、内部备注、商品/订单上下文及安全重试。微信外发、后台推送和完整多媒体接入不以这一基础版冒充已完成；前台会话刷新使用短轮询，后台推送单独验收。

本期包含：微信文字/图片双向消息、来源标记、门店分流、总部接管、内部备注、订单/商品关联、发送状态、超时提醒、配置与监控。微信语音/视频/文件收到后必须有可见类型提示，不得无声丢弃；完整播放、转写和文件预览单独验收。

本期不包含：自动退款、客服代下单/代付款、自动发优惠券、营销群发、全自动 AI 客服、有赞客服消息接入。聊天中打开现有退款/履约模块，不绕过它们的权限与审批。

## 3. 企业微信组织与实际开通

### 3.1 组织建议

优先用总部一个企业微信组织，在内部建立总部客服及各门店部门；每名员工使用自己的账号。不同门店营业执照不等于必须分别建立客服企业。独立法人门店人员加入统一组织的授权、人员管理和客户信息处理协议由企业确认，不擅自把关联主体的数据全部开放。

建立“BOOMER OFF 官方客服”及各门店客服账号。门店入口映射 ERP 的 inv_locations.id，不把店名字符串、有赞门店 ID 和 ERP 库位 ID 混用。总部客服人员及权限在 ERP 中配置。

门店无配置时，进入官方客服并显示正确的咨询归属；不能随机选一家已配置门店。总部仓库咨询归总部，保留原始库存位置。

### 3.2 企业微信管理员需要完成的步骤

1. 注册或复用总部企业微信，完成微信客服要求的企业认证及主体核验；先核对现有账号，避免重复注册和重复付费。
2. 在管理后台的微信客服应用开通客服能力，创建官方及试点门店客服账号，配置对外名称、头像、客服链接。
3. 创建“BOOMER ERP 客服”自建应用，在微信客服的“可调用接口的应用”中授权它；应用可见范围覆盖需要参与的人员。
4. 将试点客服账号设置为通过该自建应用 API 管理。此操作会改变原生接待规则，只能在 ERP 接收、回复和故障切换验收后启用，不对全部门店一次切换。
5. 配置生产 HTTPS 回调、校验 Token、EncodingAESKey；如后台要求可信 IP，使用腾讯云服务器实际出口，不使用 Lovable 动态出口。
6. 核对小程序接入权限、后台关联条件与客户端版本要求；调用 wx.openCustomerServiceChat，使用已配置的 corpId 和官方生成的客服链接。
7. 需要微信与 APP 关联同一客户时，核对小程序、微信开放平台和企业微信的关联条件及可取得的可信身份标识。拿不到时保持独立身份，不阻止匿名咨询。

代码团队负责回调、API、ERP 设置、测试与腾讯发布；企业管理员负责企业认证、员工邀请与渠道授权。密钥通过安全配置界面注入，不发送到聊天，不写入 GitHub。

## 4. 客户入口、身份与订单隐私

### 4.1 消费者看到什么

- 小程序商品页：客服按钮携带商品上下文；进入微信会话，ERP 显示商品图、标题、编码、售卖门店。
- 小程序门店页：进入该门店客服；不是通用 open-type=contact 自动混入小程序另一套客服。
- 小程序订单页：携带已验证的订单或门店履约单；多门店总订单问题默认总部协调，单店发货问题归履约门店。
- APP：原生聊天、消息列表、未读提醒；回复由同一个 ERP 工作台处理。不强制安装或跳转微信。
- 无登录用户：可以咨询商品；不能读取私有订单、收货信息、会员资产。

创建客服上下文由服务器验证归属，微信入口只携带短期、随机且无明文客户信息的场景标识。场景标识用于咨询上下文，不能单独作为微信身份绑定、订单授权或付款依据。

### 4.2 不错误合并客户

身份映射唯一键包括渠道、企业 ID、外部客户 ID；APP 使用已认证 commerce_customers.id。不按昵称、头像、用户自行填写的手机号合并。

跨渠道关联必须有可信平台身份或双方登录验证和必要的用户确认。即使关联了同一客户，各渠道会话历史仍独立标记，不能把微信私人对话无条件同步展示给 APP，反之亦然。

### 4.3 多门店订单

总部可查看授权范围内总订单并协调。门店仅见本店商品行、履约任务和完成任务所必需的收货资料，不因总订单 ID 而获得其他门店会话和客户信息。

商品调拨后，未成交商品咨询的新路由可按最新库位更新；已付款订单的客服归属按订单履约记录，已有会话转派需留审计，不静默改门店。

## 5. 接待与总部兜底规则

### 5.1 分流顺序

1. 已授权的门店履约单或售后工单。
2. 单门店订单；总订单跨门店或资金争议归总部。
3. 商品当前有效售卖门店。
4. 用户选择的门店。
5. 无明确门店或门店关闭，归总部。

入口客服账号与场景归属矛盾时，不相信客户端门店参数；进入总部核对队列，并记录原因。

### 5.2 内部状态与负责人

ERP 状态：待分配、待接待、处理中、待客户回复、已解决。超时升级是一个标记和路由事件，不创建第二份客户会话。

每个会话有一个主接待人，另有协作成员。总部可查看、写内部备注、申请/执行接管。只有主接待人可对外回复；总部需点击接管后回复。被接管员工输入中的草稿保留，发送时重新校验负责人版本，防止旧页面继续发送。

客户所在门店字段保持不变；总部接手只改变接待队列和人员，不改变订单门店、库存或分账归属。

### 5.3 建议首版默认时限

| 条件 | 动作 |
| --- | --- |
| 门店不营业、全部离线或标记忙碌 | 直接进入总部队列，不让客户先白等 |
| 客户首次发消息后 60 秒无领取 | 升级到总部并通知值班客服 |
| 领取后 120 秒无首次有效回复 | 提醒主接待人 |
| 客户等待有效回复超过 180 秒 | 升级总部可接管队列 |
| 总部也无人接待 | 显示真实服务时间、保留留言、通知值班负责人；不假装已有人工接待 |

以上为建议默认值，按门店营业时间和实际人力调整。自动欢迎语、内部备注、仅点击领取不算有效回复；客户连发消息不重置首次等待时刻。时限判断使用服务器时间，不能依赖员工手机持续亮屏。

重连、页面切换和重复定时任务不得再次转派。同一超时事件只升级一次；总部接管后不自动弹回门店。客户新问题进入同会话或新工单需显式业务规则，不能跨门店按“最近一条”复用。

## 6. 微信平台限制及可靠投递

这是实施前必须明确的技术边界。

### 6.1 ERP 人工客服不等于微信平台的人工状态

官方 send_msg 当前仅允许微信会话处于 0（未处理）或 1（智能助手接待）时使用 API 回复。首版 ERP 统一接待使用 API 可回复状态，由真实员工在 ERP 回复；“智能助手”是平台状态，不意味着必须让 AI 回答。

ERP 的员工领取、门店转总部，只改变内部负责人。不把微信会话转到 3（企业微信客户端人工接待）后还继续从 ERP 调用 send_msg。切到企业微信备用接待时，必须暂停 ERP 对外发送，显示当前由企业微信接待并同步可取得的历史。重新回到 ERP 必须按官方支持的状态转换和实测结果执行，不能臆造 3→1 自动恢复。

### 6.2 时效、限额和消息状态

官方 API 回复受客户最后主动发消息后的 48 小时及最多 5 条下行消息限制，客户继续发消息后再按官方规则获得回复机会。发送前校验平台状态、窗口和额度，欢迎语/图片等分别计入实际平台规则，不拆成多条浪费额度，不靠营销通知绕过。

超过窗口显示“微信渠道当前不可回复”，保留员工草稿；等待客户再次发消息，或按已取得授权的其他方式跟进。不把窗口限制伪装成网络故障。

消息状态区分：排队中、发送中、平台已接受、发送失败、结果待核查。API 返回成功不代表客户已收到或已读；没有平台依据不得显示已读。同步发送失败事件，失败提示具体原因并允许合规重试。

### 6.3 收消息与发送设计

回调验签解密并校验 Corp ID → 持久化 inbox/任务 → 快速响应平台 → 按客服账号串行 sync_msg 分页 → 去重入消息库 → 原子提交游标 → 更新会话和通知。

仅复用现有任务租约和数据库去重的工程模式，不能照搬有赞验签算法。微信回调必须实现自己的官方签名、AES 解密、长度/填充与 Corp ID 校验，并覆盖伪造消息测试。

拉取必须持续到 has_more=0，不以空页作为结束。失败保留原游标、指数退避并报警。回调 Token 及时使用，过期后按官方限频规则补拉。窗口补拉不能覆盖整个历史；官方可拉取最近三天，超过窗口造成的缺口必须明确报告。

ERP 回复先写消息与 outbox 同一事务，后台发送；使用稳定的平台 msgid。网络超时不能换新 ID 盲发，也不能把重复 ID 错误当成成功；保留“结果待核查”，按平台能提供的事件和窄范围实测恢复。API 外发消息不会由 sync_msg 完整回流，外发内容必须本地保存。

内部备注永不进入外发队列；附件签名与权限同样隔离。图片生成压缩预览、点击放大再取授权大图，不为会话列表重复下载原图。

### 6.4 消息通知

前台 ERP 网页和 APP 使用授权实时更新，加上重连后的增量补拉。断线显示离线状态，恢复后根据游标补齐；未读按用户已读位置计算，不按设备共用一个已读值。

ERP iPhone 后台通知需要 APNs 和相应发布配置；Android 根据实际商米/手机设备采用可用通知通道，不能假设全部设备有 Google 推送。网页未取得通知权限或已关闭，不承诺仍能可靠弹窗。员工在线定义结合心跳、接待开关和设备状态，而非“登录过”。

消费者 APP 后台提醒单独接入对应系统通知。微信客户沿用微信通知，但不保证客户端操作系统一定展示提醒。

## 7. ERP 工作台与后台设置

### 7.1 客服工作台

左侧会话列表：待接待、处理中、超时、待客户回复、已解决；总部增加全部门店筛选，门店只能筛选已授权范围。

中间聊天：客户消息、对外回复、清楚区分的内部备注、发送状态、主接待人、接管记录、输入草稿。跨设备显示协作者正在输入，但最终仍在服务器验证回复权。

右侧上下文：商品图/名称/稳定条码/售价/成色/真实瑕疵、对应门店和可售库存；订单、门店履约单、物流、售后、客户已授权身份。会员积分与券只读引用现有资产模块，不由聊天接口改余额。

移动 ERP 保留当前底部栏，用消息入口进入客户消息；详情中的上下文抽屉展开，不重新设计整套导航。内部运营通知和客户聊天分组，避免把调拨通知当客户会话。

### 7.2 专门适配中古店

快捷问题和回复模板包括：成色/划痕、尺寸与测量图、年代证据、品牌/IP、配件完整度、单件库存、到店自提、包装与易碎品运输。稀缺、绝版、真伪等措辞不得自动编造。

客户问某一件孤品时，始终携带同一 SKU ID 与条码；售出/调拨后更新提示。客服不能仅凭口头承诺锁库存，要走现有可审计的订单/锁库能力。

### 7.3 后台六个设置区域

| 区域 | 可配置内容 |
| --- | --- |
| 渠道接入 | 企业标识、凭证配置状态、回调验证、客服账号、测试结果 |
| 门店映射 | 门店/库位、微信客服入口、官方兜底账号、启用状态 |
| 接待人员 | 员工、门店范围、总部范围、接管权限、并发上限 |
| 分流规则 | 营业时间、忙碌/离线、超时时限、总部队列 |
| 快捷回复 | 通用及门店模板、内部备注模板；不自动承诺退款或鉴定 |
| 运行监控 | 回调延迟、游标补拉、消息失败、待核查外发、超时积压、配置错误 |

### 7.4 权限与审计

管理员管理渠道配置，不等于所有员工均可看到所有客户。总部客服按授权看全部业务；店员只看对应门店，协作邀请不得扩大跨店权限。

记录领取、接管、转派、回复、关闭、重新打开及配置变更，保留操作者和版本。日志只留必要元数据；不记录密钥、完整收货地址、消息原文及签名 URL。聊天/附件留存期限在上线前按客服与售后需求配置并核对隐私告知，不默认永久保存。

## 8. 数据、接口与代码边界

### 8.1 增量数据设计

| 数据对象 | 主要字段/约束 |
| --- | --- |
| 现有 support_conversations 扩展 | channel、location_id、context_type/id、primary_agent_id、queue_scope、state、assignment_version、waiting_since、last_customer_at、last_effective_reply_at、escalated_at |
| 现有 support_messages 扩展 | message_type、provider_msg_id、direction、delivery_status、failure_code、client_op_id；服务端保证内部消息不可外发 |
| 现有 support_agents/participants | 员工范围、回复权限、协作权限、在线/接待状态；保留历史身份 |
| support_channel_accounts | corp_id、open_kfid、客服链接、门店映射、启用状态；凭证只引用秘密配置，不明文存表 |
| support_channel_identities | 渠道/企业/外部用户唯一键、可空 customer_id、verified_at、绑定凭据来源 |
| support_channel_sessions | 渠道账号、外部用户、平台会话周期、ERP conversation_id；不混淆平台状态和 ERP 工单状态 |
| support_delivery_jobs | 收取/发送 durable job、去重键、重试次数、下次时间、状态、租约；收发方向隔离 |
| support_channel_cursors | 按渠道账号唯一的游标、最近成功时间、同步租约 |
| support_assignment_events | 会话负责人变化、版本、原因、操作者、幂等事件键 |

最终迁移先核对实际表结构再确定，允许在不改变语义的情况下减少表数量；不得重复创建已有同类字段。现有历史会话先标为 legacy/native 渠道，禁止反向发送历史消息到微信。

事务保证消息与外发任务同时落库；领取/转派使用版本比较和数据库事务。入站 provider_msg_id、客户端操作 ID、任务去重键均需数据库约束，不仅 Map 内去重。所有新增表默认不开客户直接写权限，RLS 与服务器鉴权双重检查。

### 8.2 接口建议

- 消费者：创建/读取/发送会话沿用现有 storefront/support 接口，补齐商品/订单/履约上下文与归属验证。
- 小程序入口：新增服务端客服入口解析接口，仅返回公开 Corp ID、合法客服链接和不含隐私的场景信息；未配置返回明确可重试状态。
- 微信回调：新增 GET 验证、POST 加密事件入口；公网可达但无有效签名不能入库。
- ERP：领取、接管、协作、关闭、忙碌状态、增量消息接口；写操作有幂等键和 assignment_version。
- 设置：只有配置管理员可读写；密钥读接口仅返回已配置/未配置，不返回原值。

## 9. 实施批次与发布门槛

| 批次 | 实施内容 | 进入下一批的证据 |
| --- | --- | --- |
| M0 契约与权限审查 | 真实数据库、账号权限、门店映射、现有上下文串线检查；冻结 UI 与接口 | 只读 SQL、字段差异表、可回复的微信状态表、隐私矩阵 |
| M1 ERP 基础闭环 | 修会话复用/上下文；主接待人、备注隔离、总部接管、路由与超时；原生客服可用 | 两门店+总部授权和并发测试，客户看不到备注 |
| M2 微信单店试点 | 官方账号+一家门店；加密回调、拉取、outbox、文字/图片、限额与故障处理 | 真实微信双向消息、总部接管、断网恢复和错误状态证据 |
| M3 客服工作台与通知 | 网页、ERP iPhone/Android，真实后台通知验证、订单上下文与监控 | 多设备重连、后台提醒、跨店订单遮蔽、无重复回复 |
| M4 消费者 APP 与扩店 | APP 原生客服、可信身份关联；逐店启用微信入口 | APP/小程序不同渠道一处接待；试点稳定后逐店放量 |

不在未取得企业微信权限前承诺日历交付时间。M1 不依赖微信凭证可先完成；M2 的真实验收依赖管理员开通和测试账号。每批单独提供代码提交、数据库变更、测试记录、线上版本和未完成项，不用“已经打通”概括局部通过。

代码由 Codex 完成并协调 Git；嵌入 Supabase 的结构核实和迁移通过已连接 Lovable 直接沟通，用户不用转述。ERP 服务部署到既有腾讯云 erp.boomeroff.com，不以 Lovable Publish 代替。未来数据库迁移时保留统一 UUID、稳定接口、任务与游标一起迁移，不借本期启动全库迁移。

发布采用独立候选目录，保留已有生产热修和私人环境文件；增量迁移先兼容旧版本。仅启用一个生产 worker 消费同一队列，数据库租约防止多实例重复处理。验证后切流，保留回滚目录和账号级功能开关。

回滚应用不删除新增消息和已发送记录；暂停失败渠道外发，保留队列并避免旧代码重发。可将该客服账号切换至官方原生接待，但需按当时后台权限和状态实测，不能直接关掉 API 规则造成无人接待。

## 10. 必须通过的验收场景

| 场景 | 必须看到的结果 |
| --- | --- |
| 小程序咨询新天地商品 | 进入正确客服入口，ERP 新天地收到，其他店不可见；总部可见 |
| 小程序咨询另一门店商品 | 不复用上一店的开放会话，不出现上一商品/订单 |
| 未登录咨询 | 可问商品，不能显示他人订单与会员信息 |
| 跨店总订单/单店履约 | 总部处理总订单；门店只见本店履约范围 |
| 同时领取/总部接管 | 一个有效主接待人；旧负责人发送被拒，草稿保留 |
| 门店无人/忙碌 | 自动到总部；没有复制会话或改变库存门店 |
| 自动欢迎语后超时 | 仍按人工有效回复等待时长升级 |
| 内部备注与图片 | 消费者接口、微信 outbox、外部附件链接均无法获取 |
| 重复回调、空分页、乱序事件 | 不重复消息、不提前停拉，游标不丢失，最近消息预览不倒退 |
| 发送请求网络超时 | 不显示假成功、不换新 ID 自动重复发，进入可诊断状态 |
| 平台发送失败/48 小时/额度用完 | 准确展示限制，保留草稿，无死循环重试 |
| worker 重启/多实例 | 持久任务继续执行，无同一任务并发发送 |
| 企业微信备用模式 | ERP 不再同时发送；切换/恢复状态有明确证据 |
| 微信绑定与 APP | 无验证不合并；绑定后统一员工工作台仍区分渠道 |
| ERP APP 退后台 | 在有授权通知配置的真机收到通知；未配置不冒称通过 |
| 图片列表、重进、放大 | 默认压缩图，有缓存；未授权资源不可读，重进不重复原图下载 |
| 生产回滚 | 能恢复服务，历史消息、游标与外发记录保留，无回放群发 |

正常网络条件下的建议目标：服务端可用后消息到 ERP 前台 P95 小于 3 秒；会话首屏 P95 小于 1 秒；60 秒无领取升级任务在阈值后 15 秒内执行。分别记录客户端端到端和服务端时延；第三方链路、弱网、后台通知不设不可能的绝对保证。没有真实成功样本不算达标。

上线观察至少覆盖一个完整营业日的单店试点，并演练一次总部接管和一次断网重连。期间监控消息失败、超时积压、错误路由、重复回复、投递待核查；存在跨店泄漏、内部备注外发、丢消息或双重发送任一项时停止扩店。

## 11. 官方依据与当前交付边界

- [微信客服概述](https://developer.work.weixin.qq.com/document/path/94638)：API 授权与账号管理模式；API 管理时原生接待规则暂停。

- [发送消息](https://developer.work.weixin.qq.com/document/path/94677)：可调用状态、回复额度/窗口和发送失败事件。

本轮通过读取官方页面原文核对上述边界，检查本地源码，并取得 Lovable 嵌入数据库只读核查报告。管理员实际权限、腾讯运行版本与数据库契约一致性、微信真机双向消息、生产通知和正式发布尚需分批验收。本轮只交付方案，不修改线上配置、不迁移数据库、不发送客户消息。
